# Backtest performance review

Where does wall-clock latency go inside TradeMaster's in-process Python-and-Rust backtest engine, and which hot-path optimizations deliver measurable speedups without altering a single order, fill, or cent of closing equity? Following three independent code reviews at commit `5dc86ce`—covering the Python strategy/result SDK, the Rust daily loop, and snapshot loading and replay—paired A/B benchmarks isolated bottlenecks across real 15-year market histories and 1,000-stock synthetic portfolios. All measurements ran on an AMD Ryzen 7 8845H under WSL2 with Python 3.12 and the release-optimized Rust extension; the primary real-data workload spans 3,644 Shanghai sessions, 14 cash distributions, and daily strategy callbacks, starting each warm-snapshot run with a fresh account. [Benchmark inputs and reference results](../examples/broad-etf.md)

## Real data

| Experiment | Original | Prototype | What was timed |
|---|---:|---:|---|
| Skip settlement audit records on opens with no lots to unlock, SSE 50 timing | 62.21 ms | 57.96 ms | Full Python SDK run on an open snapshot, detailed ledger, 11 paired runs |
| Same change, buy and hold the ETF | 46.98 ms | 35.22 ms | Same market and settings |
| Read feature columns directly, ETF snapshot | 66.40 ms | 48.85 ms | Opening and verifying the snapshot, nine paired runs |
| Same change, original single-stock snapshot | 76.03 ms | 68.69 ms | Same loading procedure |
| Update the three MACD averages as new prices arrive | 5.43 ms | 2.23 ms | Real 98-session five-stock snapshot, original strategy versus the new README implementation, detailed SDK result, 35 paired runs |

Each experiment evaluated a single isolated change against its own baseline in alternating A/B order after warm-up, preserving bit-identical targets and Rust ledgers across the settlement and MACD runs as well as identical prices and point-in-time (PIT) as-of features in the loader benchmark (note that 98-session five-stock runs were too short to show a consistent signal for the settlement change):

- **Idle-open settlement (`46.98 ms → 35.22 ms` on ETF buy-and-hold):** On every session after the first, the daily snapshot loop previously called into lot settlement even when zero T+1 lots were due to unlock—constructing and hashing a full account snapshot solely to return an empty effect (`3,641` uneventful openings in buy-and-hold and `3,569` in timing). Fast-pathing openings with no unlocking lots inside the snapshot loop—while retaining monotonic timestamp validation—eliminates that hashing overhead; production adoption must preserve the legacy event runner's audit records alongside T+1 settlement lag, dividend accrual timing, and partial-run diagnostics. [Daily loop](../../crates/tm-engine/src/snapshot/mod.rs) · [Lot settlement](../../crates/tm-engine/src/lib.rs)
- **Columnar snapshot feature loading (`66.40 ms → 48.85 ms` on ETF open):** Opening a fresh data snapshot previously sorted the feature Parquet table and materialized a Python `dict` per row; micro-profiling on the ETF snapshot showed Arrow sorting took just `0.18 ms` and SHA-256 verification of both files took `0.49 ms`, whereas row-dictionary materialization consumed `20.33 ms`. Reading typed Arrow columns directly while preserving timezone-aware `available_at` watermarks trims cold-open latency by roughly 26% (warm runs already share the opened market). [Feature loading](../../python/trademaster/backtest/snapshot.py)
- **Incremental indicator state and result construction (`5.43 ms → 2.23 ms` on 98-session MACD):** Rewriting the README and default snapshot MACD strategy to update its three exponential moving averages incrementally per close—seeding from the first complete window and resetting cleanly across missing bars—more than halved detailed runtime compared with rescanning full visible history. Separately, running a single precomputed buy-and-hold target over 3,644 sessions in summary mode took `26.92 ms` total, of which `6.66 ms` went to Python result wrapper construction—pointing to single-pass daily valuation conversion (while preserving exact `Decimal` figures and incomplete-run summaries) as a follow-up optimization. [Strategy calculation](../../python/trademaster/strategies/demo.py) · [Result construction](../../python/trademaster/backtest/__init__.py)

## Broad portfolios and the event runner

Synthetic stress tests and archived broad-universe traces highlighted three additional scaling bottlenecks:

- **Priority-queue residual lot sizing (`69.90 ms → 1.27 ms` at 1,000 candidates):** After rounding initial buy targets down to whole lots, the Rust allocator distributes leftover cash one lot at a time across candidates ranked by remaining value shortfall. On a two-day synthetic portfolio of 1,000 equal-weight buy candidates where 500 residual lots remained affordable (with opening fills blocked to isolate sizing), repeated linear scans inspected `501,000` candidate entries; replacing that scan with a max-heap ordered by remaining shortfall and instrument ID cut median detailed session time from `69.90 ms` to `1.27 ms` across 11 paired runs while matching JSON output bit-for-bit across this case and 48 randomized fixtures. With 200 candidates, runtime fell from `2.03 ms` to `0.61 ms` when ~10% of buys filled, whereas allowing all 200 buys yielded overlapping distributions (`32.40 ms` vs. `33.93 ms`) dominated by ledger postings rather than sizing. [Lot allocation](../../crates/tm-engine/src/snapshot/sizing.rs)
- **Broad-universe Python decision views (`99.9 ms` / `145.5 ms`):** Constructing Python `day` views across a synthetic 252-session, 5,000-stock calendar with static listings took `99.9 ms`, rising to `145.5 ms` when strategies queried `day.instruments` membership at every close—indicating that caching the ordered tuple and membership set between listing-lifecycle transitions will noticeably accelerate full-market Python callbacks. [Decision views](../../python/trademaster/backtest/snapshot.py)
- **Legacy event-runner validation and history slicing:** In the separate saved-event runner, validating symbols and trading dates via linear search over already-sorted arrays performed `16,775,758` symbol comparisons across `169,393` bars in an archived 201-stock run (reducible via binary search), while an archived ten-industry run copied `35.24 million` historical bar structs across `893` scheduled events—overhead avoidable via borrowed slice views for strategies that read only the current bar (end-to-end replay wall times remain to be benchmarked). [Event loop](../../crates/tm-engine/src/lib.rs) · [Event request decoder](../../crates/tm-runner/src/lib.rs)
