# M6 全链路 E2E 实施规格

Status: completed
Owner: Codex

## 目标

把已经分别验证的 M1 数据、M2 因子/信号、M3-M4 Rust 事件运行时与 M5 报告接成同一条
可执行链路，产出内容寻址、可复读的 run bundle。E2E 同时覆盖全 A 股横截面调仓形态和
单股票/ETF 买卖点形态，并至少有一个真实 Tushare 缓存优先数据案例。

## 冻结接口与边界

- Python `RunnerRequest` 绑定 run/strategy/snapshot identity、初始现金、instrument specs、
  session bars 和 signals；benchmark/classification 是报告输入，exposures 必须由 Rust 账户快照与
  实际持仓市值派生。所有时间 UTC、价格/金额 fixed-8、数量整数。
- Rust `tm-runner` 从 canonical JSON request 读取市场与信号，唯一地调用 M4 `EventLoop`，
  输出 canonical JSON result；Python 不实现第二套现金/持仓撮合引擎。
- Python orchestrator 保存 request/result SHA-256，生成现有十一表 run artifacts 或显式记录
  runner trace 所能支持的冻结子集，并由正式 verifier 复读；随后从 authoritative result
  构造 M5 report。
- E2E 输出目录不包含 token、provider response secret 或隐式本机绝对路径。

## 场景

1. synthetic cross-sectional：至少 3 个标的、多个 session，close 后信号最早 next open，
   周期性换仓，覆盖 100 股整数手、T+1、费用、换手、行业/市值暴露和 benchmark 对比。
2. synthetic single-instrument：股票/ETF 买卖点，覆盖成交、无信号日及最终持仓/NAV。
3. real Tushare cache-first：从仓库外 token 读取真实 `trade_cal` 与小范围 daily/ETF daily；
   第二次运行必须命中 Parquet/DuckDB 缓存且 formal snapshot identity 稳定。

## TDD 顺序

1. Red：runner wire 的 canonical/unknown-field/time/value validation。
2. Green：Rust CLI adapter 只做解析、构造 M4 domain objects、执行和 canonical result 输出。
3. Red：Python orchestrator 对 request/result hash、runner failure、identity/report binding。
4. Green：可复读 run bundle 与 report。
5. Red/Green：两类 synthetic strategies 的完整链路。
6. 真实 Tushare cache-first E2E；全仓库门禁；然后且仅然后一次全局高强度 fresh review。

## 完成门禁

- 两类策略均从 data/snapshot/factor-or-signal input 经 Rust runtime 到 report，不以分离的
  Python/Rust smoke 冒充完整链路。
- T-close/next-open、涨跌停/停牌、100 股、T+1 和交易成本至少各有 E2E 或已有同 runtime
  regression 证据。
- real Tushare run 未 skip，二次调用有可观测 cache hit 且 token 不进入仓库/artifacts/logs。
- request/result/artifact/report identities 可复算，E2E output 可在新进程复读。
- Python/Rust/full packaging gates 全绿后，完成一次最终全局 review；集中修复阻断项后复跑
  E2E 与门禁，不启动递归 review 链。
