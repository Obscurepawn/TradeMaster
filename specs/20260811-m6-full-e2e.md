# M6 end-to-end backtests

Status: completed
Owner: Codex

## Scope and interfaces

Connect M1 data, M2 factors and signals, the M3–M4 Rust runtime and M5 reports. Produce a content-addressed run bundle that a fresh process can read and verify. Cover both cross-sectional A-share rebalancing and trading a single stock or ETF, including a cache-first run with real Tushare data.

- The Python `RunnerRequest` identifies the run, strategy and market snapshot. It includes initial cash, instrument specifications, session bars and signals. Times are UTC, money and prices use eight decimal places, and quantities are integers. Benchmarks and classifications are report inputs. Calculate exposures from Rust account snapshots and the market value of actual holdings.
- Rust `tm-runner` reads market data and signals from canonical JSON, calls the M4 `EventLoop` and returns canonical JSON. Rust validates and executes each order and updates the ledger.
- The Python orchestrator saves the request and result SHA-256 hashes. It writes the eleven existing run artifact tables or explicitly identifies the subset supported by the runner trace. The verifier reads the artifacts back. M5 builds the report from the Rust result.
- Keep tokens, secrets in provider responses and implicit absolute paths on the local machine out of the output directory.

## Scenarios and acceptance criteria

1. **Synthetic cross-section.** Rebalance at least three instruments over multiple sessions. A signal formed after the close first becomes eligible at the next open. Cover 100-share lots, T+1 settlement, fees, turnover, sector and market-cap exposures, and benchmark comparison.
2. **Synthetic single instrument.** Exercise stock or ETF buy and sell signals, fills, days without signals, final holdings and NAV.
3. **Real Tushare.** Read credentials from outside the repository. Fetch `trade_cal` and a small set of stock and ETF daily bars. Observe a Parquet/DuckDB cache hit on the second run and verify the same snapshot identity.

Both strategy types must run from data, snapshot and factor or signal inputs through Rust to the report. Cover close-to-next-open execution, price limits, suspensions, board lots, T+1 and costs in an end-to-end test or an existing regression using the same runtime. The real Tushare test must run without a skip or token disclosure. A new process must be able to read the output and recompute request, result, artifact and report identities.

## Implementation and review order

1. Write failing tests for canonical runner requests, unknown fields, times and values. Implement the Rust CLI to parse the request, construct M4 objects, execute them and serialize the result.
2. Write failing Python tests for request/result hashes, subprocess failure and report/identity checks. Implement bundle replay and the report.
3. Exercise both synthetic strategies, then run the real Tushare cache-first case and the full Python, Rust and package checks. Conduct one final independent review after those checks pass. Fix its blockers and rerun the tests. The user chose to end the review there.

## Results and verification

M0–M5 were complete before integration. The first positive Rust wire test failed against the runner stub. The implementation then invoked the existing `EventLoop` and rejected unknown fields, noncanonical scaled integers and unknown instruments. Python test collection initially failed because `trademaster.e2e` did not exist. The subsequent tests covered subprocess errors, hashes, allocation in board lots, deterministic reports and bundle verification.

A signal formed at the close uses that day's data snapshot. Execution at the next open uses the next day's prices. The original identity check incorrectly required these snapshots to match. The request now carries each signal's snapshot ID, and the bundle records it alongside the execution snapshot.

- The synthetic three-instrument case completed two rebalances and exited all holdings in the same Rust runtime.
- The real cross-section ranked `600000.SH/600036.SH/601318.SH` by momentum on adjusted prices and selected the top two. The benchmark was `000016.SH`. Three signals produced two orders and two fills, zero rejections and two final holdings.
- The `510300.SH` ETF case used a threshold on raw closing prices and an ETF buy-and-hold benchmark. Two signals produced two orders and two fills, zero rejections and no final holdings. The ETF sale incurred zero stamp duty and transfer fee.
- Both real cases used raw, staging and canonical Parquet, DuckDB/PIT snapshots, M2 factors/signals, Rust and standalone HTML.

The one global review found 1 Critical, 4 High and 2 Medium issues. They concerned missing links between bundle inputs and outputs, stock fees applied to ETFs, missing rebalance/exit coverage, hard-coded exposures, an unpersisted Rust audit trace, and incomplete report charts and price-adjustment evidence. After the fixes, the result saved signals, orders, acceptances, executions, ledger effects and account snapshots. Verification read the snapshot manifests and Parquet files, replayed Rust, recalculated exposures from account state and rebuilt the HTML byte for byte.

A fresh process verified both bundles under `artifacts/e2e-real/` with `verify_e2e_bundle()`. It checked the bytes and SHA-256 of the snapshot objects, request, result, report inputs and report, then reran Rust and rebuilt the report. After fetching the final 7 pages, the provider call count stayed at 7 on the in-process replay. The fresh process made 0 calls. Request and result hashes matched across runs for both scenarios. The credential scan found no token value in the repository, data or artifacts.
